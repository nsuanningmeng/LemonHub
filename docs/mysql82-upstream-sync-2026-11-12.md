## 夹具与比较范围

两条路径使用各自的 MySQL 8.2 容器和命名卷，主库与日志库分开连接。每条路径均为 **主库 51 表、64 行，独立日志库 2 表、2 行，所有表非空**。入口旧结构共 681 列，原主分支及候选共 683 列。

夹具包括账户、API Token、密码哈希、会话、外部身份绑定、自定义权限、渠道、充值、订阅及结算回执、任务账本、统计、工单及附件记录、奖励活动、已领取/待领取奖励、持续发放状态和候选领取人、主/日志库的持久化奖励事件。包含 NULL、Unicode、精确小数和超出 int32 的金额/计数；账户及 Token 的余额均为 `5000000007`。

比较全部已有行的全部字段，并检查列顺序、类型、默认值、NULL 属性、字符集/排序规则、索引及前缀长度、表引擎/行格式/属性、自增值和 `SHOW CREATE TABLE`。整数不经浮点转换，Decimal 保留精确字符串；不以表数或行数相等代替内容比较。采集时关闭会话元数据统计缓存，先读取表数据，再读取自增和表结构。

只有以下精确例外：

1. **仅入口 `4751f44e3` 路径**追加 `lemonhub_upgrade_main.logs.is_retry` 和 `lemonhub_upgrade_log.logs.is_retry`，即隔离主库和独立日志库各一个同名字段，并非两个不同的新字段。两列均为 `tinyint(1) DEFAULT NULL`，位于原列之后，全部历史行的新值严格为 SQL NULL。此变更来自已拉取的原 LemonHub 主分支，本轮上游移植没有新增持久化列。
2. 当前测试节点 `upgrade-test-node` 的运行信息、启动时间、心跳时间及对应 `updated_at` 可变；节点名称、创建时间和其他节点的全部字段保持不变。
3. 仅三个精确的内置权限元组 `(p, role:admin, channel, read/operate/write, allow, '', '')` 允许重建数值行 ID，权限内容不变；全部自定义权限逐字段保留。`casbin_rule`、`authz_roles`、`external_identity_claims` 自增值只允许单调增加。
4. 恢复备份时，仅允许等价的显式默认字符集 DDL 表示差异，同时严格核对实际列字符集/排序规则、类型、索引和其他元数据。

夹具将正常清理的到期时间、奖励队列重试时间和调度时间显式设定，隔离应用迁移与正常后台业务处理。没有排除整张权限表、日志表或奖励表。数据及附件共四个文件哨兵，在候选验证前固定哈希，之后每次应用启动前和停止后都强制检查存在性与哈希；缺失时立即失败，不能自动补建。恢复后的候选继续使用原应用数据/附件目录。

## 原生回归与独立复核

冻结产品归档上的数据库矩阵通过 **149 个 MySQL 叶子用例、23 个 SQLite 对照、11 个纯逻辑用例**，合计 **183 个叶子用例、219 条含父项的 pass 记录**，所有测试进程退出 0，无失败、无必需目标缺失。覆盖：

- 旧表宽文本/小数保护、宽钱包/Token、历史日志列、统计持久化、UTF-8/GBK 性能身份、会话、订阅回执及并发结算、通知配置、工单清理、渠道排序。
- 奖励迁移保留、活动边界、并发发放/领取、迟到事件、独立进程重启恢复。
- 新缓存完整性在真实 MySQL 上的八个场景，包括篡改权限、会话撤销、预扣期间修复、不可读余额不得从陈旧数据库快照重置。
- 渠道创建 ID 返回、51 项跨批次插入、真实数据库错误回滚与 panic 回滚，以及既有权限原子初始化、GitHub 身份绑定和站点隔离。

明确跳过未配置的 PostgreSQL/ClickHouse 场景、MySQL 5.7 专用 large-prefix 场景、由父用例启动的奖励子进程辅助入口；不计为通过。汇总见 `native-final-counts.json`、`native-final-summary.json`。GitHub 旧测试只接受固定回环端口，使用本任务的临时 `127.0.0.1:33957` 转发到自有入口 MySQL 8.2，并校验实际版本；测试结束关闭转发，没有连接原开发库的 33980 端口。全部测试使用各自显式命名的隔离 schema。

现有 Compose 只读预检 **7 项通过**。比较器 **17 种故意破坏全部被拒绝**，包括余额、奖励、NULL、列、索引、权限、其他节点、DDL、自增倒退、入口新增字段的非 NULL 历史值/错误默认值及恢复中的实际字符集改变；另有缺失文件哨兵的拒绝验证。

独立审查曾指出测试脚本会在下一次启动补建缺失哨兵，可能掩盖首次删除。该问题在候选首次运行前修复，并通过负向检查及独立复核。旧基线首轮还因当前节点 `updated_at` 心跳未列入运行字段而被严格比较拦截；核实后只补齐该节点这一字段，再对原始 `seeded → normalized → baseline` 快照重新比较通过，没有行删除或其他数据归一化，也没有修改产品代码。原失败证据保留。独立方法审查报告为 `review-mysql-independent.md`。

## 结论范围与证据

本轮证明：在上述代表性数据、相同 MySQL 8.2 引擎与原连接/持久化卷、密钥保持、正常排空的条件下，替换应用镜像保留了应用表历史数据。比较范围是应用表的行、列、索引和 DDL；未验证生产实际卷绑定、所有非标准历史 schema、数据库级自定义例程/事件/触发器、大规模在途负载、磁盘故障、MySQL 引擎跨版本升级或生产停机预算。没有对未连接的生产库作无条件零丢失保证。实际更新继续使用部署原配置和原数据卷，具体预检见 [MySQL 升级预检](mysql-compose-upgrade-preflight.md)。

原始证据目录为 `/workspace/scratch/upstream-sync-2026-11-12/db/`，含源码/前端清单、产物身份、SQL 备份、全部阶段快照、原生 JSON 测试日志、比较结果和资源清单；独立审查报告在其上级目录。测试凭据及 SQL 原文只留在受限工作目录，不提交仓库。
