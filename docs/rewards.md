# 奖励中心

管理员通过侧边栏「奖励中心」（`/reward-campaigns`）创建活动；用户通过「我的奖励」（`/rewards`）领取。

## 发放

1. 输入活动名称、说明，选择「奖励金」或「拼手气红包」。奖励金设置每人固定金额；红包设置每人随机金额的上下限。输入金额单位为 USD，后台转换为现有钱包的整数额度。
2. 选择筛选时段和发放对象：成功充值用户、成功调用用户、成功充值用户和成功调用用户（交集），或成功充值用户或成功调用用户（并集）。「和」要求两类记录都发生在所选时段内，「或」满足任意一类即可。界面显示浏览器本地时区，范围包含开始时间、不包含结束时间。
3. 设置每份奖励的有效天数（默认 7 天，可输入 1–3650 的整数），奖励金和红包均适用。每个用户从自己实际获发的时刻开始按每 24 小时为一天计算，后续加入者不会沿用活动创建时的截止时间。
4. 确认创建持续活动。预览是可选的当前人数／预计金额提示，不是创建前置条件，也不锁定最终人数；当前 0 人或全未来时段同样可以创建。已有符合条件记录先由后台分批发放，活动期间后来满足条件的用户继续自动获发。

所有发放对象都必须是**已启用、未删除的主站用户**，停用用户不参与预览和发放，实际发放时再次锁定并检查用户状态。充值按支付完成时间筛选，仅包含成功且没有退款扣回的订单；调用按消费日志时间筛选，错误日志不计入。同一用户同时满足两种条件也只收到一份奖励。调用记录使用项目配置的日志数据库；初次回填只读取仍保留的记录，未记录的调用不参与筛选。后台已接收的活动证据和候选资格会持久化，因此事件重试不依赖内存或重新扫描全部日志。

新界面创建的活动明确发送 `continuous=true`，活动期间所有符合条件用户均可获得一份，不设业务总份数或总金额上限；固定金额和每人红包上下限保持不变，不重分已发金额。最终成本随参与人数增加，当前预览金额不代表最终预算。每个人的钱包及单份奖励仍受原有安全额度约束。后台批次大小只控制单轮工作量，剩余用户会继续处理，不会截断名单。创建请求使用 `request_id` 防止网络重试产生重复活动，账本的活动／用户唯一约束防止重复奖励。

活动时间范围决定哪些充值／调用记录有资格，包含开始、不包含结束。开始时间在未来时先等待；结束后仍可处理属于该时段的积压记录。`completed` 表示活动时段已结束，不保证队列已经清空；恢复时不会把结束前已符合条件的用户丢弃。

升级前的活动保持原来的一次性名单，即使其结束时间在未来也不会重新激活。省略 `continuous` 或显式 `false` 的旧 API 请求继续使用一次性发放规则与兼容校验。

发放记录按活动显示**已领取人数**和**共计已领取金额**，只统计领取成功且已入账的奖励。`claimed_quota_exact` 始终返回累计整数额度的精确十进制字符串；在 JavaScript 安全整数范围内，旧 `claimed_quota` 数值保持不变，超出范围时返回 `null`，不能把舍入值或上限值当成实际金额。红包按实际抽中金额累计，不使用配置上限或预算估算；重复领取不会重复计数。用户领取后再被停用或删除，其历史领取仍保留在统计中。记录页每 30 秒自动更新，重新切回窗口时也会刷新。

## 领取

- 登录后发现待领取奖励会自动弹窗；已在线的用户每 30 秒检查新奖励，侧边栏同步显示待领取数量。
- 「稍后领取」暂缓当前已知奖励在本浏览器会话中的自动提醒；用户仍可随时进入「我的奖励」手动领取。新发放的奖励仍会提醒。
- 固定奖励领取后直接加入账户余额；红包在领取时由服务端在配置范围内抽取整数额度，包含上下限，领取前不产生中奖金额。
- 领取状态、中奖金额和钱包加款在同一数据库事务中提交。重复领取返回之前的结果；事务失败不改变余额或奖励状态。提交后同步现有余额缓存，领取明细作为主库内的持久记录，并附加系统日志。
- 红包底部以小字显示到期时间，使用浏览器本地时间；待领取卡片也显示截止时间。
- 到期时刻起不能再领取，服务端在领取事务内校验，过期不会抽奖入账，也不会增加已领取人数或金额。过期奖励不计入待领取数量、不再自动提醒，可在历史记录中查看。
- 领取有效时刻以事务内的服务端校验为准：取得锁后、确定金额后以及写入钱包后均检查截止时间，最后一次校验必须严格早于 `expires_at` 才允许提交。若钱包写入后已到期，奖励记录和余额一起回滚；不以网络响应或物理 COMMIT 完成的时刻判定有效期。
- 已成功领取的奖励不受后续到期影响，重复请求仍返回之前的结果，不会重复入账。发放请求重试也不会延长原到期时间。

## 接入与升级

服务启动迁移会更新奖励活动表并新增分发进度、候选和来源事件小表。`continuous` 默认关闭，不通过历史 `end_time` 推断或修改旧活动。旧 `user_rewards` 的名单、金额、领取状态、实际领取额和原 `expires_at` 原样保留，`expires_at=0` 的旧用户奖励仍无期限；新创建活动必须提交有效天数。

`user_rewards` 是已发奖励的持久事实，包含已领取和未领取记录。停止或重启应用、更新程序不会重新抽取已领取金额，也不会重置已发未领取奖励的有效期；个人奖励页面重新从数据库加载。分发游标、候选和待处理来源事件也持久化在数据库，失败后可以安全重放；缓存与进程内任务不是事实来源。以上保障以保留数据库及其持久卷为前提，删除或替换数据库不属于应用重启。红包金额仍在用户首次成功领取时抽取，发放和重启都不提前抽奖。

后台复用 SystemTask 的多实例租约与恢复机制。初次调用记录回填使用现有 `(created_at,id)` 时间索引（ClickHouse 使用时间和 request_id），只读窄列并记录分页游标；充值历史按已有主键和创建活动后捕获的上界分批遍历一次，在批内过滤完成时间，不自动对旧大表建立新索引。后续充值状态变化和消费日志通过持久来源事件处理，不周期重扫整站日志、不依赖最大事件 ID 或有限回看窗口。关系型来源写入与事件入队同事务；ClickHouse 使用主库预写意图，并按原始时间及请求 ID 确认来源。每次主库幂等分发完成后才确认事件。

所有写入节点必须完成本版本升级后再创建持续活动：混用旧版写入节点时，旧节点不会生成来源事件，不能保证持续活动补发。该限制不影响旧一次性活动及已发奖励的保留。所有应用节点必须完成来源捕获初始化；缺少必要事件表时启动报错，不能静默遗漏。需要主节点运行后台 SystemTask。领取仍使用原来的登录、鉴权、限流和钱包事务。隔离小库测试不代表 800 GB 生产库或一分钟升级窗口已验证，历史充值的一次遍历耗时取决于实际数据量；分批进度可以恢复。

| 接口 | 用途 |
| --- | --- |
| `GET /api/rewards/summary` | 当前用户待领取数量及固定奖励总额度 |
| `GET /api/rewards` | 当前用户分页奖励；可按 `status`（`pending`、`claimed`、`expired`）、`type` 筛选 |
| `POST /api/rewards/:id/claim` | 领取本人奖励，返回奖励结果及最新钱包额度 |
| `POST /api/reward-campaigns/preview` | 管理员预览符合条件人数 |
| `POST /api/reward-campaigns` | 管理员注册持续活动，发送 `continuous=true` 与 `expires_in_days`；预览可选，持续模式忽略兼容字段 `expected_recipient_count` |
| `GET /api/reward-campaigns` | 管理员分页查看发放记录，含累计 `recipient_count`、`claimed_count`、`claimed_quota_exact`、兼容 `claimed_quota` 及 `distribution_status` |

列表分页使用 `p`、`page_size`。API 金额字段均为钱包整数额度，时间为 Unix 秒，用户奖励的 `expires_at` 是自己的领取截止时间；新持续活动的 `expires_at=0` 表示没有统一截止，使用 `expires_in_days` 展示每份有效期。活动状态为 `scheduled`（等待开始）、`backfilling`（历史分批发放）、`active`（时段进行中）、`completed`（时段已结束）或 `legacy`（旧一次性活动）。个人奖励到期状态按服务端当前时间计算，不依赖定时任务。管理员及个人设置中均可控制对应侧边栏入口的显示。

## 数据库回归验证

MySQL 专项测试使用 `MYSQL_REWARD_TEST_DSN` 指向**新建、空的** `lemonhub_rewards_test_*` 数据库；测试会拒绝其他库名或非空库，只清理测试创建的表。不要使用应用数据库或现有数据卷。

```sh
go test ./model -run '^(TestMySQLReward.*|TestRewardClaimExpiryBoundaries)$' -count=1 -v
```

覆盖升级前奖励表的完整数据保留、两次迁移幂等、旧零值有效期、不同 MySQL 连接竞争领取及重复发放，以及领取事务跨截止时刻的余额与统计回滚。时间边界测试只控制外部时钟和抽奖熵，数据库事务真实执行，不依赖睡眠或概率性的并发压力。
