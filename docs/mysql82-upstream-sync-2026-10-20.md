# MySQL 8.2 应用镜像升级验证（2026-10-20）

本次验证对应 [上游选择性同步](upstream-sync-2026-10-20.md)。旧应用基线为 `50c357aeb07a5f3d95e31b8b5f4fd799ef264388`，新应用为本次同步后的代码；两者均重新构建完整前后端。没有连接、升级或写入用户的生产数据库。

## 代码与部署边界

本次同步没有修改数据库模型、启动迁移、Dockerfile、Compose、数据库连接及挂载约定。新通知偏好保存在既有用户设置 JSON，邮件供应商配置保存在既有 `options` 表；不重写旧通知偏好、定价、余额、账单或渠道密钥。

渠道优先级只在管理员明确操作时更新，`channels` 与 `abilities` 同事务提交；预览不写入，冲突拒绝，NULL 可保留及撤销。邮件供应商配置写入时，在事务内锁定完整配置组，基于数据库当前值校验，避免多个应用节点用各自的旧缓存写坏有效配置。

## 隔离测试方法

- 使用官方 `mysql:8.2`，记录实际服务器版本、镜像 ID、server UUID 和 `/var/lib/mysql` 挂载。所有测试容器和卷均由本任务创建并校验所有权，现有开发数据库不参与。
- 旧源码由 Git 归档，并逐文件核对受控内容；使用 Go 1.26.9、`CGO_ENABLED=0`、`GOEXPERIMENT=greenteagc` 和 Bun 构建。验收镜像复用这些构建产物，使用生产 Dockerfile 相同的固定 Debian 基础镜像、运行时软件包、许可证、工作目录和入口。它们是隔离验收镜像，不是已发布镜像；没有声称执行了原 Dockerfile 的全部多阶段构建。
- 旧应用初始化主库和独立日志库后，写入覆盖每张表的合成记录，包括中文和 emoji、NULL、超过 32 位的余额、原密码哈希和 API Token、订单、订阅回执、会话、工单及异常渠道设置。应用数据目录和附件目录各有文件哨兵。
- 每次比较全部行和字段，并比较列定义、索引、建表语句、表属性和自增状态；不能以表数或行数一致代替数据比较。
- 停止应用写入后，使用 `mysqldump --default-character-set=utf8mb4` 备份，再恢复到全新独立卷。要求数据及有效表结构完全一致，保留原始快照。恢复后的建表文本可能显式补写同一 `CHARACTER SET utf8mb4`；只有列属性、索引、表属性和全部行均严格相等，且去除这一冗余声明后全文相等时，才记录为表示等价。
- 应用启动阶段仅允许已核实的运行节点信息/心跳、内置 root/admin 策略的数值行 ID，以及 `casbin_rule`、`authz_roles`、`external_identity_claims` 的自增计数单调增加；策略内容、业务记录和原业务 ID 仍严格比较。每项允许变化均记录实际值。
- 替换应用镜像后重复启动，另做 MySQL 同镜像同卷重建及升级后备份恢复。恢复后实际使用旧 API Token、旧密码登录并访问用户资料，核对余额和 Token 剩余额度。

原生数据库回归另用独立临时 schema，覆盖历史迁移、身份/排序规则、日志、订阅回执、64 位钱包/Token、会话、工单并发清理、权限初始化和新增渠道排序。原始日志显式检查指定测试确实通过，不能把未配置 DSN 导致的跳过当作成功。

## 实际部署仍需核对

本轮没有用户的生产 Compose、实际镜像和挂载快照，不能据隔离测试断言任意生产更新都不会丢数据。实际更新应继续使用 [已有只读预检与升级步骤](mysql-compose-upgrade-preflight.md)：

1. 保留原 MySQL 实例、库名、server UUID、数据卷和应用/附件挂载，保留原 Compose 项目名、连接、网络及加密密钥。
2. 排空所有应用实例的在途写入，再停应用备份主库、独立日志库和文件；备份放在原卷之外，并实际验证恢复。
3. 固定新应用镜像，只更新应用服务，例如在已核对的原配置下执行 `up -d --no-deps`。不要用仓库 PostgreSQL 示例覆盖现有 MySQL 部署，也不要执行 `down -v` 或删除原数据卷。

测试验证已提交数据的保留。批量额度更新和异步退款尚未落库时，强杀或断电仍有既有风险；本轮没有将这些路径改造成持久化队列。既有过期数据与孤立文件清理也仍遵循原规则。

## 验收结果
