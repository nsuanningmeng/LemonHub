# 模型性能统计与升级说明

## 渠道状态与历史数据

性能样本按「渠道、模型、分组、时间桶」记录。查询分组明细、模型总成功率和趋势时，统一读取数据库当前渠道状态，同时过滤已落库和内存中的样本：

- 手动禁用或已删除的渠道不参与统计，包括该渠道禁用前的记录。
- 手动重新启用渠道后，统计窗口内保留的历史记录重新参与统计。
- 自动禁用渠道的已有失败记录仍保留在可用模型分组的统计中，避免通过自动停用隐藏故障。
- 模型当前已移除或用户无权使用的分组仍由现有可用分组规则排除。
- 渠道状态查询失败时返回查询错误，不展示未经渠道过滤的统计。

已启用渠道的手动、批量和定时测试会将健康结果分配给配置的所有模型和分组。批量测试执行前和统计写入前重新读取渠道状态；禁用渠道的恢复探测不增加性能样本。自动停用和恢复只能更新未被手动禁用的渠道，不能覆盖人工禁用决定。

## 速度指标的含义

测试响应解析成功后，在记录消费日志前保存实测输出 token 数和耗时：

- TPS 使用输出 token 数除以生成耗时；流式请求从首响应计生成耗时，非流式请求使用总响应耗时。
- 首 Token 延迟沿用网关首流式响应的计时语义。非流式请求没有这一测量值。
- 一次测试的速度指标只归入实际测试的模型及其配置分组。其他模型得到健康结果，不能借用被测模型的速度。
- 状态码未命中失败白名单的错误可以按规则计为成功，但不会因此生成不存在的 TPS 或首 Token 延迟。
- 没有有效输出 token 数时没有 TPS；没有流式首响应时没有首 Token 延迟。页面以 `—` 表示未测得，而不是数值 0。

手动渠道测试默认仍为非流式；需要首 Token 延迟时，应选择目标模型并开启流式测试。自动测试保留现有协议选择，避免让不支持流式的端点因统计需求而失败。

## 首次升级的数据处理

旧 `perf_metrics` 表已将不同渠道合并为模型/分组汇总，没有渠道标识，无法准确拆出手动禁用渠道的贡献。直接将这类数据归给某一渠道会导致错误统计。

新版本创建 `channel_perf_metrics` 表，旧表原样保留，不删除、不猜测回填，也不混入新的性能页面。升级后性能统计会从新记录开始累计；执行渠道测试或产生实际请求即可建立新样本。旧消费日志和用户账务不受此统计表切换影响。

多实例部署需将所有应用实例升级到同一版本。旧实例仍写入旧表，其样本不会进入新版本统计；新旧实例混用会导致看到的数据不完整。新表使用 SQLite、MySQL、PostgreSQL 均支持的普通列、复合唯一索引和 GORM 查询。
