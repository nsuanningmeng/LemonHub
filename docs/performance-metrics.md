# 模型性能统计与升级说明

## 批量查询 API

`GET /api/perf-metrics/models` 一次返回用户可用的各模型、各分组的成功率和性能指标。默认累计统计最近 24 小时，采用与模型广场分组详情相同的查询边界和样本加权口径。接口始终要求用户鉴权，不受模型广场是否允许匿名访问的设置影响。

使用用户访问令牌（`User.AccessToken`，面板 PAT）发送 `Authorization: Bearer <PAT>`，也支持有效的面板登录 JWT；无需 `New-Api-User` 请求头。模型调用用的 `sk-` API Key 不适用于此接口。已有的 `GET /api/user/token` 可在用户鉴权后生成 PAT；再次调用会替换旧 PAT。

| 查询参数 | 说明 |
| --- | --- |
| `hours` | 可选，累计统计最近多少小时；默认 `24`，必须为 `1`～`720` 的整数，只能出现一次 |
| `model` | 可选，精确匹配模型名称；省略或为空时查询全部可用模型 |
| `group` | 可选，精确匹配分组名称；省略或为空时查询全部可用分组 |

```bash
curl --get 'https://your-domain.example/api/perf-metrics/models' \
  --header "Authorization: Bearer ${USER_ACCESS_TOKEN}" \
  --data-urlencode 'model=gpt-4o'
```

默认查询的响应示例：

```json
{
  "success": true,
  "message": "",
  "data": {
    "hours": 24,
    "start_time": 1735691400,
    "end_time": 1735777800,
    "bucket_seconds": 3600,
    "models": [
      {
        "model_name": "gpt-4o",
        "groups": [
          {
            "group": "default",
            "has_data": true,
            "success_rate": 99.5,
            "avg_latency_ms": 2400,
            "avg_ttft_ms": 350,
            "avg_tps": 48.25
          },
          {
            "group": "premium",
            "has_data": false,
            "success_rate": null,
            "avg_latency_ms": null,
            "avg_ttft_ms": null,
            "avg_tps": null
          }
        ]
      }
    ]
  }
}
```

显式添加 `--data-urlencode 'hours=24'` 与默认查询口径相同；修改该参数可查询其他小时数。

模型按名称、分组按名称升序排列。模型和分组的可见范围与模型广场一致：必须属于模型当前启用的分组、存在有效分组倍率，且用户有权使用；不返回 `auto` 虚拟分组。`model` 和 `group` 只能缩小范围。不存在或无权访问的筛选条件返回成功响应及 `models: []`。

统计反映共享上游渠道的整体表现，包含实际请求和渠道测试，不是当前用户的个人调用统计。接口不返回请求数量、成功数量、渠道标识或其他用户信息。

| 指标 | 计算口径 |
| --- | --- |
| `has_data` | 查询范围内是否存在有效样本 |
| `success_rate` | 成功样本数 ÷ 总样本数 × 100，单位为百分比 |
| `avg_latency_ms` | 总响应耗时 ÷ 总样本数，单位为毫秒，整数截断 |
| `avg_ttft_ms` | 实测首 Token 延迟总和 ÷ 有首响应计时的流式样本数，单位为毫秒，整数截断 |
| `avg_tps` | 有效速度样本的输出 token 总数 ÷ 生成总耗时（秒），单位为 token/s |

各分组先合并查询范围内有效渠道和时间桶的样本，再计算指标；例如成功率为成功样本数之和除以总样本数之和，与模型广场分组详情一致，不对各渠道或时间桶的平均值做简单平均。成功判定沿用采样时的失败状态码白名单：白名单为空时所有失败均计入；配置白名单后，未命中的错误可计为成功。该比率不等同于严格的 HTTP 2xx 比率。

可用分组即使没有样本也会返回，此时 `has_data` 为 `false`，所有指标为 `null`。已有样本但没有实测首 Token 延迟或有效速度时，对应指标仍为 `null`；实测首 Token 延迟为零时返回 `0`。全部失败的样本返回 `success_rate: 0`，与无数据区分。接口不应用前端“无数据显示为 100%”设置，也不提供当前未采集的 P95/P99 等分位指标。

`start_time` 和 `end_time` 是实际查询边界的 Unix 秒时间戳（UTC）：结束时间为统计生成时刻（命中缓存时保留原时间），起始时间为结束时间减去 `hours × 3600`，不向下对齐时间桶。与模型广场一样，只纳入起点时间满足 `start_time <= bucket_ts <= end_time` 的桶，包括当前桶；早于查询起点但与查询范围部分重叠的桶不计入，也不按请求计算部分桶。本接口不提供逐请求精确时间切片。

`bucket_seconds` 为当前配置的时间桶长度，默认一小时；配置支持 `minute`（60 秒）、`5min`（300 秒）和 `hour`（3600 秒）。配置变更后，历史桶长度可能不同，不能用当前 `bucket_seconds` 推断历史桶范围。

数据合并数据库中已落库的样本和当前节点尚未落库的样本。本节点刷盘与查询通过版本校验和必要的重读协调，避免同一批样本在内存清空与数据库落库之间漏算或重复统计；多节点的其他节点样本需等其落库后才可见。成功响应最多缓存 30 秒，不承诺跨节点事务级实时快照。

错误响应使用 `success: false`。无令牌、无效令牌或已禁用账号返回 `401`；`hours` 为空、重复、非整数或越界时返回 `400`（`code: INVALID_HOURS`）；性能数据查询失败返回 `500`（`code: PERF_METRICS_QUERY_FAILED`）；统计查询并发已满时返回 `503`（`code: PERF_METRICS_BUSY`，`Retry-After: 1`）。限流返回 `429` 并带有 `Retry-After`，可能在鉴权或参数校验前触发。数据库错误详情只写服务端日志。

## 查询频率与服务器保护

以下保护覆盖 `/api/perf-metrics`、`/api/perf-metrics/summary` 和 `/api/perf-metrics/models`：

- 三个接口共用每 IP 每分钟 120 次的专用限额，在用户鉴权前检查；设置环境变量 `PERF_METRICS_IP_RATE_LIMIT` 可调整。
- `/models` 另外限制每个已认证用户每分钟 60 次，切换访问令牌或 IP 不会重置用户限额；设置 `PERF_METRICS_USER_RATE_LIMIT` 可调整。
- 专用限流不依赖全局 API 限流开关；上述配置在路由初始化时读取，非正数回退默认值。启用 Redis 时限额跨节点共享，否则各节点独立计数。Redis 使用固定窗口，窗口边界可能短时突发；内存限流使用滑动窗口。
- 成功响应在当前节点缓存 30 秒，同一有效参数和可见模型/分组范围的并发请求合并查询。失败结果缓存 2 秒，防止数据库故障时重复重试。鉴权和可见范围每次重新计算；权限范围变化后不会命中原范围的响应。
- 不同统计查询每节点最多并发 4 个，满载时立即返回 `503`。等待相同查询结果的请求每节点合计最多 64 个，最多等待 5 秒，满额或超时也返回 `503`，不无限排队。缓存最多保留 128 项、16 MiB 的响应内容；超大的单条响应不进入缓存。

建议客户端至少间隔 30 秒轮询，收到 `429` 或 `503` 后按 `Retry-After` 退避重试，避免无间隔重试。频繁切换参数不会绕过 IP/用户限额及查询并发上限。样本或渠道状态变化最多需等待 30 秒的缓存刷新；不同接口的缓存生成时间可能稍有差异，但统计窗口和加权口径保持一致。

接口发送 `Cache-Control: no-store` 等响应头，禁止浏览器和共享代理缓存权限相关数据。此限制不影响服务端按当前权限范围复用上述短期缓存。

## 渠道状态与历史数据

性能样本按「渠道、模型、分组、时间桶」记录。生成分组明细、模型总成功率和趋势的统计时，统一读取数据库当前渠道状态，同时过滤已落库和内存中的样本：

- 手动禁用或已删除的渠道不参与统计，包括该渠道禁用前的记录。
- 手动重新启用渠道后，统计窗口内保留的历史记录重新参与统计。
- 自动禁用渠道的已有失败记录仍保留在可用模型分组的统计中，避免通过自动停用隐藏故障。
- 模型当前已移除或用户无权使用的分组仍由现有可用分组规则排除。
- 渠道状态查询失败时返回查询错误，不展示未经渠道过滤的统计。

已启用渠道的手动、批量和定时测试会将健康结果分配给配置的所有模型和分组。批量测试执行前和统计写入前重新读取渠道状态；禁用渠道的恢复探测不增加性能样本。自动停用和恢复只能更新未被手动禁用的渠道，不能覆盖人工禁用决定。

## 速度指标的含义

测试响应解析成功后，在记录消费日志前保存实测输出 token 数和耗时：

- TPS 使用输出 token 数除以生成耗时；流式请求从首响应计生成耗时，非流式请求使用总响应耗时。
- 首 Token 延迟沿用网关首流式响应的计时语义。非流式请求没有这一测量值。
- 一次测试的速度指标只归入实际测试的模型及其配置分组。其他模型得到健康结果，不能借用被测模型的速度。
- 状态码未命中失败白名单的错误可以按规则计为成功，但不会因此生成不存在的 TPS 或首 Token 延迟。
- 没有有效输出 token 数时没有 TPS；没有流式首响应时没有首 Token 延迟。页面以 `—` 表示未测得，而不是数值 0。

手动渠道测试默认仍为非流式；需要首 Token 延迟时，应选择目标模型并开启流式测试。自动测试保留现有协议选择，避免让不支持流式的端点因统计需求而失败。

## 首次升级的数据处理

旧 `perf_metrics` 表已将不同渠道合并为模型/分组汇总，没有渠道标识，无法准确拆出手动禁用渠道的贡献。直接将这类数据归给某一渠道会导致错误统计。

新版本创建 `channel_perf_metrics` 表，旧表原样保留，不删除、不猜测回填，也不混入新的性能页面。升级后性能统计会从新记录开始累计；执行渠道测试或产生实际请求即可建立新样本。旧消费日志和用户账务不受此统计表切换影响。

多实例部署需将所有应用实例升级到同一版本。旧实例仍写入旧表，其样本不会进入新版本统计；新旧实例混用会导致看到的数据不完整。新表使用 SQLite、MySQL、PostgreSQL 均支持的普通列、复合唯一索引和 GORM 查询。

## 模型与分组标识的精确匹配升级

模型名和分组名按原始字符串精确区分，包含大小写、重音字符和尾随空格。MySQL 默认排序规则可能把不同字符串当成相同值；查询层保留原有索引过滤，并追加精确比较和分组，防止不属于用户可见范围的样本被合并进结果。

写入层使用模型名与分组名的 SHA-256 标识 `identity_hash`，与渠道和时间桶构成唯一键。已有 `channel_perf_metrics` 表升级时先新增可空标识列和新索引，分批回填已有行，再移除旧字符串唯一索引；保留原始名称、统计计数及查询索引。迁移失败会中止启动，可在处理原因后重新启动继续，成功迁移可重复执行。

升级时需将全部节点更新到同一版本，再恢复对外服务；旧节点未计算新标识，不能与新节点长期混写。如果升级前 MySQL 已把同一渠道、同一时间桶的不同名称样本合并为一行，现有汇总数据无法恢复各名称的原始计数。升级保留这些历史汇总，新的写入不会再发生此类合并；历史影响随统计窗口滚动移出。
