# MySQL 8.2 应用镜像更新验证（2026-10-23～24）

本报告对应选择性同步阶段的候选。后续发布审查另有代码与依赖修复，最终 v0.5.6 产物的独立复验见 [发行候选 MySQL 报告](mysql82-release-v0.5.6-2026-10-24.md)，不能混用两次产物身份。

**隔离测试通过：本次镜像更新保留了全部已有业务数据。用户的约 800 GB、单实例、最多 60 秒中断的生产部署尚未验收，不能把下述小样本耗时视为生产停机承诺。**

本报告对应 [本轮上游同步](upstream-sync-2026-10-23.md)。未连接、备份、修改或升级生产数据库；已有开发 MySQL 8.4 容器也未参与测试。

## 数据与比较规则

基线为主库 **46 表、587 列、54 行**，独立日志库 **1 表、23 列、1 行**，所有表均有记录。夹具包含 267 个 NULL、16 个超出 int32 的整数及 12 个 Unicode 字段，并保留真实密码哈希、API Token、超过 32 位的账户/令牌余额、订单、订阅回执、身份绑定、会话、工单和渠道配置。数据目录及附件目录各有文件哨兵。

比较全部行的全部字段，并比较列顺序、类型、默认值、NULL 属性、字符集/排序规则、索引及前缀长度、表属性、自增状态和 `SHOW CREATE TABLE`。二进制字段以十六进制保存；数值不经浮点转换。表数或行数相同不是通过依据。

仅有下列经过源码检查的例外：

1. 本次更新在 `quota_data` 新增 `cache_read_tokens`、`cache_creation_tokens` 两个 `bigint DEFAULT 0` 字段；全部历史行的新字段严格等于 0，旧字段和索引不变。
2. 启动时当前测试节点的运行信息、启动时间和心跳可变；其它节点和字段仍严格比较。内置 root/admin 权限规则可重新生成数值行 ID，但规则内容不能变；`authz_roles`、`casbin_rule`、`external_identity_claims` 自增值只允许单调增长。
3. 跨日恢复后首启触发原有 30 分钟模型检查调度。仅首次候选启动允许新增 **1 条**已到期的 `model_update` 成功任务：原任务逐字段不变，新 ID 必须等于原自增值，自增恰好加 1，任务 ID/执行节点格式正确，时间在该容器启停窗口内，状态和结果全部精确匹配“0 个渠道、0 项变更”。其它阶段不允许这个例外。
4. 备份恢复时，仅在全部行、列属性、索引及表属性一致的前提下，接受 MySQL 为原有列显式补写等价 `CHARACTER SET utf8mb4` 的 DDL 表示差异。

升级后共 **47 表、612 列、56 行**；增加的两列与一条正常调度任务均已逐项核对，没有删除或重写原业务行。最终真实登录会按原业务逻辑新增认证会话/登录日志并更新登录时间，这发生在完整数据比较之后；另外核对旧密码哈希、Token 及余额未改变。

## 800 GB、单实例与 60 秒中断预算

本轮仅有 55 条已有记录。以下时间从创建测试应用容器开始，到 `/api/status` 返回成功为止，包含本地启动/迁移；停止时间取正常停止空闲测试容器。**不含 800 GB 数据备份、恢复、生产负载排空或大表演练。**

| 测试阶段 | 就绪秒数 | 正常停止秒数 |
| --- | ---: | ---: |
| 首次更新应用镜像 | 3.206 | 0.379 |
| 候选应用再次启动 | 6.867 | 0.395 |
| MySQL 同卷重建后启动 | 2.143 | 0.171 |
| 备份恢复到新卷后启动 | 1.719 | 0.15 |
| 恢复库真实认证检查启动 | 1.918 | 0.142 |

实际测试 `quota_data` 为 Dynamic 行格式；MySQL `INNODB_TABLES.TOTAL_ROW_VERSIONS=2`，对应 GORM 两次加列的 Instant 版本。另在旧表结构副本强制 `ALGORITHM=INSTANT` 同时加两列成功，耗时约 **0.0134 秒**且旧行不变。这只证明当前夹具表结构可用，不证明生产表的行格式、版本历史、全文索引等条件相同。

当前 GORM 自动迁移没有为这两次加列强制 Instant 算法或短元数据锁等待；测试服务器默认 `lock_wait_timeout=31536000` 秒。长事务持有元数据锁、生产表不满足 Instant 条件或旧性能指标表需要创建索引/逐行回填时，都可能超过 60 秒。数据库总量 800 GB 也不能代替实际 `quota_data`、`channel_perf_metrics` 大小和表结构信息。

此外，现有 Compose 的 `stop_grace_period=130s` 配合默认 `SHUTDOWN_TIMEOUT_SECONDS=120`，本就允许在途请求和结算排空超过 60 秒。本测试为加快空闲夹具收尾使用 30 秒上限，不能把缩短生产期限或强杀进程当作实现 60 秒的方法；尚未刷入 SQL 的批量额度、异步退款与长请求仍需正常排空。

因此，本轮结论是**兼容迁移及正常镜像替换的数据保留已通过隔离验证；800 GB 单实例 60 秒窗口没有验收通过**。实际执行前仍须按 [已有 Compose/MySQL 预检指南](mysql-compose-upgrade-preflight.md) 核对原连接与数据卷、受影响表结构/大小、长事务及锁、可用备份和恢复能力，并以具有相当数据规模的克隆验证停机预算。不能以仓库默认 PostgreSQL 示例覆盖现有 MySQL 配置，或通过删除原卷更新镜像。
