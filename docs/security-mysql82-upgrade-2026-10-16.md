## 兼容影响

- 以前的 MJ 裸图片链接返回 403；重新查询已授权的任务或刷新列表可取得有效期 24 小时的链接。原任务和原媒体地址不删除。签名密钥存于既有 `options` 表，重启和多个节点复用，不新增表结构。
- 已使用 Secure Cookie 的用户升级后需重新登录一次；账户、余额和数据库中的会话记录不因此删除。多节点仍需保留一致的原 `SESSION_SECRET` / `CRYPTO_SECRET`。
- 无秘密读取权限的管理员可编辑普通渠道属性，也可明确替换隐藏配置；原配置包含重复敏感 JSON 字段时，需要明确替换该字段后再保存，避免无声覆盖。
- 发现不支持中文的旧表时启动检查会阻止继续运行并保留数据库，不能通过重新初始化来绕过；应先备份并单独处理字符集兼容。
- 前端计费预览只接受受支持的表达式语言，JavaScript 代码和不支持的语法会报错；此改动不改写已存储表达式，也不替换后端计费引擎。

## MySQL 8.2 验证口径

隔离环境使用官方 `mysql:8.2`，实测服务器为 **8.2.0**。旧应用后端来自本仓库 `b8d952a408afd1cf058da5241c8ba240feb9797c`（v0.5.3）源码重建，嵌入上轮已验证的前端产物，仅作为数据库升级基线；它不是官方 v0.5.3 完整镜像，也不代表用户尚未提供的实际生产镜像。候选验收容器使用最终 Go 可执行文件、最终前端构建和与仓库相同 digest 的 Debian 运行时；该数据库验收镜像未执行发布 Dockerfile 的 CA/tzdata 安装阶段，也未发布。

基线覆盖主库 46 表及独立日志库 1 表，共 609 列、62 行合成记录；包含中文/emoji、NULL 与零、超过 32 位的余额、原密钥与密码哈希、会话、订单、订阅回执、工单及异常渠道配置。应用持久化目录另有文件哨兵。比较表、列、索引和全部字段值，不能用“表数/行数相同”代替完整比较。

备份在停止应用写入后使用 `mysqldump --default-character-set=utf8mb4`，恢复到独立实例和全新卷；备份恢复比较不做归一化。应用启动比较只允许以下已核实变化，并在证据中列出实际值：

- 已知验收节点的运行信息和心跳时间。
- 内置角色策略重建的数值行 ID，策略内容仍严格比较。
- `casbin_rule`、`authz_roles`、`external_identity_claims` 的自增计数单调增加；原业务记录及 ID 不允许改变。后者源自既有身份导入的冲突忽略插入。
- 首次启动新增一条持久化 `MediaSigningSecret`；后续重启必须保留完全相同的值。

最终执行结果见本节下方验收表；原始证据保存在工作区 `/workspace/scratch/security-mysql82-2026-10-16/`，其中测试库凭据和 SQL 备份仅用于隔离环境，不应公开发布。

环境恢复后，两台测试数据库再次与原基线做原始快照比较，47 表、609 列、62 行完全一致。元数据快照显式关闭当前会话的 `information_schema` 统计缓存，并在只读获取全部行、打开 InnoDB 表后重新读取实时元数据。首次同卷重建检查曾因冷表返回的自增计数少 1 而停止；只读诊断证实 42 项计数在打开表后全部恢复预期，业务字段、列和索引始终不变。修正的是快照采样顺序，没有修改数据库或放宽比较；失败日志仍保留。验收夹具禁用跨日的外部模型更新调度，仍严格保留原 `system_tasks` 记录；生产默认配置不变。

## 实际 Compose 部署的数据保留条件

按 [只读预检与升级步骤](mysql-compose-upgrade-preflight.md) 执行。该脚本不会停止、创建、替换容器或写数据库；通过也不代表已完成备份、恢复验证或在途写入排空。

1. 核对原 MySQL 容器、镜像 ID、server UUID、实际库名和 `/var/lib/mysql` 的原卷/绑定目录。应用 `/data` 与数据库卷分别保留；附件目录也需备份。
2. 保留原 Compose 项目名、文件顺序、环境、网络及连接；只更新应用服务的固定镜像。仓库默认 Compose 使用 PostgreSQL，不能覆盖已有 MySQL 配置。
3. 停止所有入口写入并排空全部实例，保持 MySQL 可用；应用停止宽限大于内部退出预算。旧版本缺少的退出保护不会因准备了新镜像而自动生效，退出码 0 也不单独证明在途写入已排空。
4. 备份实际主库、独立日志库和文件目录，将备份保存在原数据卷之外，并在独立 MySQL 8.2 实例验证恢复及重要字段。
5. 再次运行预检后，仅对应用服务执行 `pull` 和 `up -d --no-deps`；核对原库与业务记录后再恢复流量。不要使用 `down -v`、删除/清理卷或删除宿主机数据库目录。

已有的工单保留策略、24 小时孤立上传清理和过期认证记录清理仍会按其规则运行，不能把主动过期清理描述为镜像升级的数据丢失。

## 仍存在的明确边界

- 已提交记录的保留与尚在内存中的操作不是同一件事。批量额度更新、尚未落库的异步退款在强杀/断电时仍有丢失窗口；因此正常排空是升级条件，超时设置不能替代持久化日志或 outbox。
- 返佣与部分业务审计在主交易提交后另行写入；尚未关联本地订单的 Stripe 乱序退款也需要对账。此次修复可重试的数据库故障，不宣称所有附加事件在任意崩溃下必达。
- 未查看生产反向代理、HTTPS/Cookie 开关、数据库权限、磁盘/备份系统和外部身份提供方配置；代码审查及测试不证明系统不存在任何未知漏洞。
- Go 模块公告扫描还需区分可达调用、导入包和仅模块存在；本轮最终扫描结果列于验收表，不能将无可达漏洞写成所有依赖不存在公告。
