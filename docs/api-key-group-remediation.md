# API 密钥空分组的存量处理

## 问题与修复范围

旧创建表单会把未选择分组表示为一个空白条目，后端此前允许将它保存为 `tokens.group = ''`。这类密钥不会使用一个名为“空白”的独立分组：鉴权时 `Token.GetGroups()` 返回空列表，实际请求继承密钥所属账户的分组，随后按该分组选择渠道和计费。

修复后的创建表单初始不选任何分组，创建和普通编辑保存必须手动选择至少一个分组；直接调用接口传入空分组也会报错。旧空组密钥允许停用，但在补充分组前不允许通过状态接口重新启用。

本次修复不自动修改、停用或重新分配存量密钥的分组。已启用的旧空组密钥仍按原有鉴权行为运行，必须按以下步骤处理。无法从空值推断用户原本希望选择的分组，不能批量写成 `default`、`auto` 或账户当前分组。

## 上线前检查

1. 部署前备份数据库，确认操作的是 LemonHub 当前部署使用的主数据库。
2. 所有应用节点部署相同版本，并确认前端静态资源也已更新。
3. 严格要求用户手选分组的部署必须保持 `GENERATE_DEFAULT_TOKEN=false`。该环境变量默认关闭；若开启，注册流程仍会自动创建初始密钥，其分组取决于 `DefaultUseAutoGroup`，属于独立的旧功能，本次未改动。
4. 确认数据库中的目标 `site_id`。下列查询默认仅检查主站 `site_id = 0`；处理子站时，把 `0` 替换为已确认的子站 ID，逐站执行，不移除站点限制。

## 只读筛选

以下查询排除已软删除的密钥，不读取或输出 `key` 字段。结果包含所有状态，避免遗漏已经停用、到期或额度用尽的待修复密钥：`status = 1` 为启用，`2` 为停用，`3` 为到期，`4` 为额度用尽。可以追加已确认的 `user_id` 或 `created_time` 范围缩小批次。

查询覆盖 `NULL`、空字符串，以及仅由逗号、普通空格、制表符或换行组成的值。本次创建接口会规范化输入，因此该问题产生的空值会被筛出。如果历史上通过导入或直接写库保存了其他 Unicode 空白字符，还需使用与 `model.Token.GetGroups()` 相同的解析规则复核，不能仅依赖 SQL 的 `TRIM`。

### PostgreSQL

```sql
SELECT t.id, t.user_id, t.site_id, t.name, t.status,
       t.created_time, t.accessed_time, t.used_quota
FROM tokens AS t
WHERE t.deleted_at IS NULL
  AND t.site_id = 0
  AND TRIM(REPLACE(REPLACE(REPLACE(REPLACE(
        COALESCE(t."group", ''), ',', ''),
        CHR(9), ''), CHR(10), ''), CHR(13), '')) = ''
ORDER BY t.user_id, t.id;
```

### MySQL 5.7.8 及以上 / SQLite

```sql
SELECT t.id, t.user_id, t.site_id, t.name, t.status,
       t.created_time, t.accessed_time, t.used_quota
FROM tokens AS t
WHERE t.deleted_at IS NULL
  AND t.site_id = 0
  AND TRIM(REPLACE(REPLACE(REPLACE(REPLACE(
        COALESCE(t.`group`, ''), ',', ''),
        CHAR(9), ''), CHAR(10), ''), CHAR(13), '')) = ''
ORDER BY t.user_id, t.id;
```

筛选结果是“需要用户确认分组”的名单，不能仅凭空值证明每条记录都由本次表单问题产生；此前的注册初始密钥或旧版继承账户分组的密钥也可能在其中。

## 推荐处理：保留原密钥，逐条手选分组

1. 按筛选结果中的 `user_id` 和密钥 `id` 确认归属，由密钥所属用户登录 API 密钥页面。
2. 打开对应密钥的编辑表单，手动选择允许使用的分组；选择多个分组时，同时确认它们的优先级顺序。
3. 保存并确认成功。编辑分组不会更换密钥字符串，也不会清空调用记录，客户端无需替换密钥。保存时保留原有名称、额度、有效期、模型限制和 IP 限制。
4. 对需要继续使用且之前已停用的密钥，在保存有效分组后手动启用；不要批量启用已经到期或额度用尽的密钥。
5. 使用原密钥进行一次预期的正常请求，确认可用性及日志中的实际分组；多分组密钥还应确认优先级符合用户选择。
6. 再次运行相同站点的只读查询，核对剩余名单。仍需保留但暂时无法确认分组的密钥可以保持停用，直到所属用户完成选择。

普通保存接口 `PUT /api/token/` 不是局部字段补丁：脚本客户端应先用 `GET /api/token/:id` 获取当前设置，再保留可编辑字段并明确更新 `group`。更推荐直接使用页面，避免仅提交 `id` 和 `group` 时覆盖其他配置。密钥接口校验当前登录用户的所有权，管理员账号不能借此直接修改其他用户的密钥。

## 需要立即阻断时

先通过页面停用名单中需要暂停的密钥，再由用户完成上面的手选与恢复步骤。停用会使后续通过鉴权的新请求失败，不会撤销已经通过鉴权的在途请求。

既有状态接口也可用于停用，使用该密钥所属用户的面板登录凭据发送：

```http
PUT /api/token/?status_only=true
Authorization: Bearer <该用户的面板访问凭据>
Content-Type: application/json

{"id": 123, "status": 2}
```

将 `123` 替换为已核对的密钥 ID；这里的面板访问凭据不是待处理的模型 API 密钥。检查响应中的 `success` 确认为 `true`，不能只看 HTTP 状态码。修复版本允许空组密钥执行这一停用操作，但会拒绝对它直接发送 `status = 1`，提示先选择分组。

## Redis 与批量处理注意事项

页面和密钥更新接口都会调用 `model.Token.Update()`，在写库前设置缓存失效栅栏并清理对应缓存，让后续读取获取新分组或新状态。开启 Redis 的部署应走这条已有更新路径。

不要直接执行 SQL 修改 `group` 或 `status` 后就认为变更已生效。密钥 Redis 哈希同时包含分组、状态和额度信息；直接写库会绕开缓存失效和并发保护，重启应用也不会清除外部 Redis 数据。不要使用 `FLUSHDB` 或批量删除 `token:*` 作为修复步骤，因为同一命名空间还存在计费与并发保护数据。

所有应用节点共享 Redis 时，更新路径能清理同一缓存。若各节点使用独立 Redis，单个节点的更新无法清理其他节点缓存，应先按部署实际情况统一缓存或制定逐节点受控失效方案，再把变更视为已经在全站生效。

该问题不需要自动数据库迁移。小批量采用页面处理；大批量先整理站点、用户和密钥 ID 清单，再按用户确认的分组逐条调用现有接口并记录成功或失败。保留只读清单即可，不导出完整密钥，不添加猜测用户分组的批量赋值脚本。
