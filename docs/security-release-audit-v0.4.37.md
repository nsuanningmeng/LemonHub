# v0.4.37 安全与数据保留审查

日期：2026-09-23。基线为 v0.4.36（`3d8880f33c7631b2421f7cdb952f69de8e8b4c41`），API 密钥分组修复提交为 `a0600e2a89c649f871e62484f392fdf5594494fa`。本记录覆盖该修复及随后审查发现的问题。

## 范围与方法

- 审查路由认证、用户及站点归属、密钥创建/编辑、日志和任务读取、支付与计费、SQL 构造、SSRF 防护、浏览器 HTML 渲染和发布工作流。
- 全仓规则扫描后人工核对高危命中；结合控制器、模型与组件回归验证真实数据流。规则扫描的固定 SQL、测试数据、PEM 标记等命中不能直接当作漏洞或自动通过证据。
- 使用 Go 官方漏洞库的 `govulncheck` 分析根模块与独立 relaykit，在 Windows/amd64 和 Linux/amd64 分别检查可达调用；前端运行 `bun audit`，桌面依赖运行 `npm audit`。
- 在独立 MySQL 实例验证真实启动迁移和重复迁移，并将命名卷保留、删除容器后重建的测试加入 CI。
- 没有访问生产数据库，没有修改生产配置或清理生产密钥、缓存和数据卷。代码审查和依赖数据库扫描不能证明不存在未知漏洞。

## 确认并修复的问题

| 问题 | 影响与修复 | 回归依据 |
| --- | --- | --- |
| 空分组密钥 | 默认 `['']` 绕过数组长度校验；初始改为空选择，前后端验证至少一个非空分组，旧空组密钥可停用但不能直接重新启用；组是否存在及用户是否有权使用仍由请求鉴权检查 | 密钥表单、批量创建、分组选择器和控制器测试 |
| 自定义页脚存储型 XSS | 站点页脚直接进入 HTML 渲染；改用 DOMPurify 净化最终进入渲染的内容 | 实际 Footer 组件验证事件属性、脚本、危险链接和 iframe 被移除，安全内容保留 |
| 私有视频共享缓存 | 需要鉴权的内容却返回公共缓存策略；改为 `private, no-store`，过滤上游及 CDN 缓存头 | HTTP 上游和 data URL 分支均断言响应头及内容 |
| 个人统计归属错误 | 用户名可同名、改名或带通配符；改用服务端认证用户 ID 同时限定额度和 RPM/TPM 聚合 | 跨站同名、通配符、历史改名和伪造查询参数用例 |
| 数据库故障提示可能诱导丢数据 | 桌面端提示删除 WAL；移除该建议，要求正常退出、保留数据库与 WAL、备份后排查 | JavaScript 语法检查；SQLite 官方说明已提交事务可能仅在 WAL 中 |

私有视频旧缓存需要部署方清除 `/v1/videos/*/content` 对应条目，更新源站响应头不会主动撤回已有 CDN 缓存。SQLite 的依据见[官方 WAL 说明](https://www.sqlite.org/wal.html)。

## 依赖处理

- Go：最低版本及 Docker builder 升级为 1.26.8；固定官方镜像摘要。更新 `gorilla/websocket` 1.5.3、`klauspost/compress` 1.18.7、`x/crypto` 0.56.0、`x/image` 0.45.0、`x/net` 0.57.0、`x/text` 0.41.0 及相应间接依赖；relaykit 独立使用 `x/text` 0.39.0。
- 前端：更新 Vitest 至 4.1.11，并锁定 Hono、Undici、Mermaid、PostCSS、YAML、URI、TOML 等受影响依赖的修复版本。最终 `bun audit --json` 返回 `{}`。
- 桌面：Electron 从 39.8.10 升至 44.4.5，更新兼容的锁文件依赖，`npm ci` 后 `npm audit --json` 已知漏洞为 0。新版 Electron 按需下载运行时，发布步骤显式执行本地安装脚本，保证附带许可证文件存在。
- 依赖报告需区分模块存在与程序实际调用。`x/crypto/openpgp` 的 GO-2026-5932 涉及废弃且无修复版本的包，当前程序未导入、不可达；不能把模块级提示描述为已修复。漏洞库解释见 [Go 官方文档](https://go.dev/doc/security/vuln/)。

本次没有实测 PostgreSQL/MariaDB 升级、生产数据规模、线上卷驱动、断电恢复或 MySQL 引擎跨大版本升级。已通过的 SQLite 单元回归与 MySQL 实例验证不能替代这些条件下的独立验收，也不能替代备份恢复演练。

## 存量密钥与部署

没有足够信息从空值推断用户本来想选择哪个分组，因此不批量写入默认组、不自动停用历史密钥。按 [存量处理方案](api-key-group-remediation.md)筛选当前站点的密钥 ID，由所属用户编辑原密钥完成选择，保留密钥字符串和余额，使用已有接口使 Redis 缓存失效。

应用容器升级应保留原 `SQL_DSN`、数据库和 MySQL `/var/lib/mysql` 挂载。升级应用不需要更换 MySQL 引擎，也不应运行 `docker compose down -v`。实际生产挂载没有经过本次连接验证，部署方仍需核对并完成备份。
